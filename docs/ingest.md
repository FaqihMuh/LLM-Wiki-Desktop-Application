# Ingest Specification

## Purpose

Define the deterministic workflow for transforming one selected research document into persistent knowledge.

Each ingest operation SHALL process exactly one source document.

The same source document SHALL NOT be ingested more than once.

---

# Authority Hierarchy

The Ingest Agent SHALL always follow, in order of priority,

1. Identity Specification
2. CLAUDE.md
3. Ingest Specification
4. User instructions

---

# Objective

Transform one research paper into reusable persistent knowledge while preserving consistency, traceability, and determinism of the wiki.

---

# Input

One selected source document: a PDF, or a supported image (PNG, JPG, JPEG).

Location:

raw/

The selected document SHALL be explicitly provided by the caller.

The caller MAY be a user or an external application.

The system SHALL process only the specified document.

The system SHALL NOT automatically determine which document to ingest.

The system SHALL NOT automatically process every PDF stored inside the raw directory.

If no document is specified,

Abort the operation and request the caller to specify a source document.

---

# Output

Updated Persistent Memory.

Execution telemetry MAY be generated by the caller but SHALL NOT become part of the Persistent Memory.

Affected resources:

* wiki/summaries/
* wiki/entities/
* wiki/index.md
* wiki/log.md

---

# Pipeline

## STATE 1

PRECHECK

↓

Load:

wiki/index.md

The loaded wiki/index.md SHALL remain the authoritative directory for the entire ingest operation.

Retain its contents in working memory.

Do NOT reload wiki/index.md unless it has already been modified during the current ingest.

Validate:

* input file exists
* input file is a supported PDF or image (PNG, JPG, JPEG)
* source registry is readable
* document has not been ingested previously

Duplicate detection priority:

1. SHA256 Hash (if available)
2. DOI
3. arXiv ID
4. Exact Title
5. Filename

If an identical document already exists in the Source Registry:

Abort the operation.

Report:

"Document already exists in the Source Registry."

Do NOT regenerate summaries.

Do NOT update entities.

Do NOT modify the index.

Do NOT append the log.

---

## STATE 2

READ_SOURCE

↓

Read the complete document.

Identify:

* title
* topic
* research objective
* methods
* core concepts
* datasets
* benchmarks
* findings
* limitations

Proceed only after the document has been fully understood.

The source document is the primary knowledge source for this ingest.

Do NOT read existing summary pages for writing style, formatting, or content validation.

Formatting is defined exclusively by docs/summary.md and docs/markdown.md.

---

## STATE 3

CREATE_SUMMARY

↓

Generate one summary page.

Follow:

docs/summary.md

The summary SHALL be generated directly from the source document.

Existing summary pages SHALL NOT be consulted as formatting examples.

The formatting specification defined in docs/summary.md is authoritative.

The summary's Related Entities section may reference only entities already known to exist in wiki/index.md as loaded during PRECHECK — the Persistent Entity Target Set for this state contains nothing else yet (see docs/entity.md § Persistent Entity Target Set). Do NOT wikilink a concept solely because it seems likely to become a new entity later in this ingest — ENTITY_RESOLUTION (STATE 5) has not run yet, and its outcome SHALL NOT be anticipated. Concepts with no persistent entity page yet may still be discussed freely in prose everywhere else in the summary — only the wikilink is deferred, not the knowledge itself. The Related Entities section is finalized later, in STATE 6, once the authoritative set for this ingest is known.

---

## STATE 4

EXTRACT_CANDIDATE_ENTITIES

↓

Follow:

docs/entity.md

Extract candidate entities from the document.

Candidate entities are temporary.

They SHALL NOT be written directly into the wiki.

Create no more than five candidate entities.

Only concepts with long-term knowledge value may become candidates.

---

## STATE 5

ENTITY_RESOLUTION

↓

For each candidate entity:

Use the Knowledge Index in wiki/index.md as the primary directory of existing entities.

Use the Knowledge Index to identify potential matching entities before opening any entity page.

Read an existing entity page ONLY when:

* the candidate is a plausible match
* the candidate may extend that entity
* additional evidence is required before deciding UPDATE or CREATE

Do NOT inspect unrelated entity pages.

Do NOT compare every entity page.

Workspace exploration SHALL NOT be used during Entity Resolution.

Determine whether the candidate is:

* an existing entity
* an alias of an existing entity
* a more specific concept of an existing entity
* a broader concept of an existing entity
* a genuinely new entity

If the candidate can reasonably extend an existing entity,

select UPDATE.

Otherwise,

select CREATE.

Creating a new entity SHALL be the last resort.

When uncertainty exists between UPDATE and CREATE,

prefer UPDATE unless there is clear evidence that the candidate satisfies the CREATE criteria defined in docs/entity.md.

This decision SHALL be based solely on the candidate's own merit — see docs/entity.md § Entity Resolution. It SHALL NOT be influenced by whether the summary (STATE 3) or any other page already discusses, mentions, or would like to link to this candidate. A dangling or deferred wikilink is never grounds for a CREATE decision.

No files are modified during this state.

The output of this state is only a decision.

---

## STATE 6

UPDATE_ENTITIES

↓

Execute the decisions produced by ENTITY_RESOLUTION.

If the decision is UPDATE:

Update the existing entity page.

Collect every required modification for the entity before editing.

Each entity page SHOULD be edited at most once during a single ingest whenever practical.

Merge all new knowledge into one coherent update.

Preserve previous verified knowledge.

Relationship Population: once every CREATE/UPDATE decision from ENTITY_RESOLUTION has been executed and every resulting entity page has been successfully written, the Persistent Entity Target Set for this ingest is final (docs/entity.md § Persistent Entity Target Set). Only now populate the summary's Related Entities section (deferred since STATE 3): wikilink a concept only if it is a member of that final set. A concept with no persistent entity page — rejected, never extracted as a candidate, or simply discussed in prose — remains ordinary text; do not wikilink it.

This step SHALL NOT create, or cause the creation of, any entity page. It only reads the already-final target set and writes links against it. If a concept the summary discusses has no persistent entity page, that is resolved by leaving it as prose — never by creating a page for it here or at any later point in this ingest. Every wikilink and `related:` entry — in the summary and in every entity page — SHALL reference only entities that actually exist at this point. See docs/entity.md § Relationship Rules.

---

## STATE 7

UPDATE_INDEX

↓

Update:

wiki/index.md

Reuse the wiki/index.md content already loaded during PRECHECK whenever possible.

Reload the file only if it has already been modified during this ingest.

The index serves two purposes.

### Source Registry

Maintain exactly one record for every successfully ingested document.

Each record SHOULD contain:

* Title
* DOI or arXiv ID (if available)
* Filename
* Summary Page
* Entity Count
* Ingest Date

Append the record as one new row in the existing `| Title | arXiv ID | Filename | Summary Page | Entities | Ingest Date |` table under `## Source Registry`. Example row for a document titled "EnvACE", arXiv ID `2608.06197`, source file `raw/2608.06197v1.pdf`, summary page `[[EnvACE]]`, 3 entities, ingested `2026-08-10`:

```
| EnvACE | 2608.06197 | 2608.06197v1.pdf | [[EnvACE]] | 3 | 2026-08-10 |
```

### Knowledge Index

Maintain:

* Summary Pages
* Entity Pages

Under `## Summary Pages`, append one `- [[Summary_Page_Name]]` bullet per summary page (matching the `[[...]]` link already used for the Summary Page column above), e.g. `- [[EnvACE]]`.

Under `## Entity Pages`, append one new row per entity in the existing `| Entity | Type | Status | Last Updated |` table, e.g.:

```
| [[EnvACE]] | Framework | Experimental | 2026-08-10 |
```

For an UPDATE decision (STATE 6) on an existing entity, update that entity's existing row in place (Status/Last Updated) rather than appending a duplicate row.

The Source Registry SHALL contain exactly one record for each ingested document.

The same document SHALL NEVER appear twice.

---

## STATE 8

UPDATE_LOG

↓

Append one chronological log entry.

The log SHALL be append-only.

Existing log entries SHALL NEVER be modified.

Each log entry SHALL contain the following sections.

### Document Information

* Timestamp
* Operation
* Document Title
* DOI or arXiv ID (if available)
* Source File
* Summary Page

### Knowledge Summary

* Created Entities
* Updated Entities
* Rejected Candidates

Rejected candidates SHOULD include the reason for rejection whenever available.

### Knowledge Statistics

* Total Summaries
* Total Entities

### Result

One of:

* SUCCESS
* ABORTED
* FAILED


---

## STATE 9

COMPLETE

↓

Persistent memory successfully updated.

---

# Entity Extraction Priority

When selecting candidate entities, prefer the following order:

1. Framework
2. Method
3. Model
4. Algorithm
5. Dataset
6. Benchmark
7. Metric
8. Task
9. Organization

Priority alone does not guarantee selection.

Each candidate SHALL satisfy the long-term knowledge criteria defined in docs/entity.md.

---

# Knowledge Integration

New knowledge SHALL extend existing knowledge.

Existing knowledge SHALL NOT be overwritten without supporting evidence.

Conflicting findings SHALL be preserved and documented.

---

# Execution Efficiency

Execution SHALL prioritize deterministic knowledge generation while minimizing unnecessary workspace exploration.

During a single ingest:

* reuse information already obtained whenever possible
* avoid rereading files that have not changed
* avoid reading unrelated summaries
* avoid reading unrelated entity pages
* avoid using workspace discovery or Glob
* avoid multiple edits to the same file whenever a single edit can achieve the same result

Reducing unnecessary tool usage SHALL NOT reduce knowledge quality.

---

# Atomic Operation

The workflow SHALL execute sequentially.

PRECHECK

↓

READ SOURCE

↓

SUMMARY

↓

EXTRACT CANDIDATE ENTITIES

↓

ENTITY RESOLUTION

↓

UPDATE ENTITIES

↓

INDEX

↓

LOG

↓

COMPLETE

If any critical step fails,

all remaining steps SHALL stop.

The wiki SHALL NEVER remain partially updated.

---

# Failure Handling

If PRECHECK fails

Abort.

---

If document reading fails

Abort.

---

If summary generation fails

Abort.

---

If candidate extraction fails

Abort.

---

If entity resolution fails

Abort.

---

If entity update fails

Abort.

---

If index update fails

Abort.

---

If log update fails

Abort.

---

Do NOT leave partially updated knowledge.

---

# Completion Criteria

The ingest operation is complete only when:

✓ Source validated

✓ Source Registry updated

✓ Summary saved

✓ Candidate entities extracted

✓ Entity resolution completed

✓ Entity pages created or updated

✓ Index updated

✓ Log updated

✓ No duplicate source records

✓ No duplicate entities

✓ No relationship (wikilink or `related:` entry) references a nonexistent entity

✓ No validation errors

Otherwise,

the ingest SHALL be considered incomplete.
